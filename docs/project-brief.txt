# PROJECT BRIEF — GOWORK

## Project Name
GoWork

## Project Type
Production-Oriented Backend Portfolio Project

## Main Goal
Build, test, containerize, document, and deploy a real HTTP backend service using Go.

This project is intended to demonstrate practical backend engineering ability, especially in:

- Go
- RESTful API
- Raw SQL
- PostgreSQL
- RBAC / authorization
- Authentication
- Testing
- Docker
- CI/CD
- Cloud deployment
- Production-oriented backend architecture

The final project must be suitable for:
- GitHub portfolio
- Backend Engineer job applications
- Technical interviews
- Demonstrating personally deployed Go HTTP service experience

The project should NOT be treated as a simple tutorial CRUD project.

---

# 1. PRODUCT OVERVIEW

GoWork is a Work Order Management backend system.

The system manages:
- users
- roles
- permissions
- assets/equipment
- work orders
- technician assignments
- work order lifecycle
- audit logs

Example use case:

A company owns operational assets such as:

- Generator A
- Pump B
- Excavator C
- Truck D

When an asset has an issue, a manager creates a work order.

Example:

Work Order:
WO-2026-001

Asset:
Generator A

Issue:
Oil pressure warning

Priority:
HIGH

Assigned Technician:
User X

Status:
ASSIGNED

The technician can then update the lifecycle:

OPEN
→ ASSIGNED
→ IN_PROGRESS
→ COMPLETED

The system must enforce authorization rules.

---

# 2. USERS AND ROLES

There are 3 main roles:

## ADMIN
Can:
- create users
- view users
- manage roles/permissions if needed
- create assets
- update assets
- delete assets
- create work orders
- assign technicians
- update work orders
- view audit logs

## MANAGER
Can:
- view users
- create assets
- update assets
- create work orders
- assign technicians
- view all work orders
- update work orders
- view audit logs

Cannot:
- delete assets
- create admin users unless explicitly designed otherwise

## TECHNICIAN
Can:
- view work orders assigned to themselves
- update status of their assigned work orders

Cannot:
- create assets
- delete assets
- create users
- update work orders assigned to another technician

# 3. PERMISSION MODEL

Permissions should be database-driven, not fully hardcoded.

Example permission codes:

work_order:assign

user:read
user:update

Tables:

roles
permissions
role_permissions

Authorization should check role permissions and, where necessary, resource ownership.

Example:

A TECHNICIAN may have:

work_order:read
work_order:update

but may only update a work order if:

work_orders.assigned_to == current_user.id

# 17. WORK ORDER BUSINESS RULES

Use explicit lifecycle rules.

Allowed:

OPEN
→ ASSIGNED

ASSIGNED
→ IN_PROGRESS

IN_PROGRESS
→ COMPLETED

Optional:

OPEN
→ CANCELLED

ASSIGNED
→ CANCELLED

IN_PROGRESS
→ CANCELLED

Invalid transitions must be rejected.

Example invalid transition:

OPEN
→ COMPLETED

Return:

409 Conflict

Example:

{
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "Cannot transition from OPEN to COMPLETED"
  }
}
